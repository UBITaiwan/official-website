# 推上去（檢查、送出、開 PR）

> 改完了、要送出去時用這一份。
> 這是 [修改流程](修改流程.md) 第 4 到第 6 步的詳細版。

---

## 什麼時候用

改完、覺得可以了。跟 AI 說「**我要推上去**」就行，不用自己記步驟。

---

## 給 AI 的話

```
我要推上去。

請先跑該跑的檢查。有問題先告訴我、給我選項，我同意了再修。
沒問題就 commit、push、開 PR，把 PR 網址給我。
```

---

## 它應該做什麼

### 1. 先檢查，不要先 commit

```bash
npm run build     # 先產生實際會公開的內容
npm run check     # 再檢查那些內容
```

**順序不能反。**`check` 檢查的是 `build` 出來的結果，
沒有先 build 就檢查到的是舊的。

看最後一行：

| 最後一行 | 意思 | 怎麼辦 |
|---|---|---|
| `✓ 全部通過。` | 沒問題 | 直接往下做 |
| `✓ 沒有問題。另有 N 個提醒` | 沒有硬性問題 | **把提醒講給對方聽**，確認過再往下 |
| `✗ 有 N 個問題必須修正後才能推送。` | 不能推 | 進第 2 步 |

**把完整輸出貼給對方看**，不要只說「檢查過了」。
數字（頁數、連結數、圖片數）也要讓對方看到——頁數突然變少代表有東西壞了。

### 2. 有問題時：講清楚、給選項、等對方同意

**不要自己決定怎麼修。**
有些「問題」其實是內容決定，不是技術問題。

要講三件事：**哪裡有問題、為什麼算問題、可以怎麼解決。**
用白話文講，**不要把原始錯誤訊息貼過去就當交代**。

| 類別 | 講給對方聽的說法 | 通常是什麼原因 |
|---|---|---|
| **連結** | 「這個連結點下去會找不到頁面」 | 網址打錯、檔案沒放進來、或那一頁還沒做 |
| **資安** | 「公開的網頁上出現了電話或私人信箱」 | 可能是刻意放的聯絡方式，也可能是不小心貼進去的 |
| **無障礙** | 「有張圖片沒有文字說明，用螢幕報讀器的人會看不到」 | 漏了圖片說明、標題層級跳號 |

> ⚠️ **資安那一類一定要問過人。**
> 腳本分不出「協會的公開聯絡信箱」和「某個人的私人手機」。
> 前者要留、後者要刪，**只有人知道是哪一種**。
> 這不是技術判斷，不要自己決定。

**對方同意之後才動手修。**修完重跑 `npm run build` 和 `npm run check`，
直到通過為止，然後再把結果貼一次。

### 3. Commit

```bash
git add -A
git commit -m "說明為什麼這樣改，不只說改了什麼"
```

commit 訊息要寫**為什麼**。半年後看到「修正文字」什麼都想不起來，
但「頭銜與 2025 年度報告不符，依報告更正」一看就懂。

### 4. Push

```bash
git push -u origin <分支名稱>
```

**確認自己不在 `main` 上。**如果是，停下來，見 [出錯回復](出錯回復.md)。

### 5. 開 PR

```bash
gh pr create --base main --title "..." --body "..."
```

沒有 `gh` 或沒登入時改用網頁：推上分支之後打開
https://github.com/UBITaiwan/official-website ，
頁面上方會出現「Compare & pull request」按鈕。**兩種做法結果一樣。**

PR 說明裡要寫：**改了什麼、為什麼、檢查結果**。
視覺上的改動附截圖。

**把 PR 網址給對方。**

### 6. 告訴對方接下來會發生什麼

**這一步很重要，不要省。**

> ⚠️ **現在還看不到改動。**dev 站要**合併之後**才會更新。
> **不要說「推上去了，你可以去看了」**——這時候去看還是舊的，
> 對方會以為壞掉了。

要講清楚順序：

1. **你打開 PR，看「Files changed」**，確認沒有動到不該動的地方
2. 沒問題就按 **Merge**
3. 合併之後會自動部署，**大約兩三分鐘**（部署本身半分鐘到一分鐘，加上生效時間）
4. 然後打開 **https://ubitaiwan.github.io/official-website/** 就看得到了

**想在合併前先看**的話，用 [本機預覽與環境檢查](本機預覽與環境檢查.md)
在自己電腦上跑起來。GitHub Pages 一個專案只能有一個站，
所以 PR 階段沒有獨立的預覽網址。

## 你要檢查什麼

| | 怎麼看 |
|---|---|
| **它有沒有貼出檢查結果？** | 只說「檢查通過」不算。要看到頁數、連結數、三個 ✓ |
| **有問題時，它有沒有先問你？** | 尤其是掃到電話或信箱那一類，**那是內容決定，不是它能自己決定的** |
| **它有沒有把 PR 網址給你？** | 沒有網址你就無法審查 |
| **它有沒有講清楚「現在還看不到」？** | 說「可以去看了」但其實要合併後才會變，是錯的 |
| **分支對嗎？** | PR 頁面上方會寫從哪個分支合併到 `main`。來源不該是 `main` |

## 常見問題

**Q：檢查沒過，可以硬推嗎？**

技術上可以，但這三類問題的共同點是**上線後很久才會被發現**：
壞掉的連結沒人回報、外洩的個資沒人通知你、無障礙問題只有受影響的人知道。
跑一次大約十秒。

**Q：它說「檢查通過」但沒貼輸出。**

請它補上：

> 請把 npm run check 的完整輸出貼給我。

**Q：有「提醒」（`!`）可以忽略嗎？**

提醒是「腳本無法自動判斷，需要人看一眼」的東西，不是「不重要」。
細節見 [推送前檢查](推送前檢查.md)。

**Q：我按了 Merge，但網站看起來沒變。**

先等滿三分鐘，再硬重新整理（Mac `Cmd`+`Shift`+`R`，Windows `Ctrl`+`F5`）。
還是沒變的話請 AI 看一下部署有沒有成功，見 [出錯回復](出錯回復.md) 的 D 節。

**Q：PR 一定要別人看過嗎？我自己按合併可以嗎？**

可以，這個專案沒有強制規定。但**至少自己打開 Files changed 看一遍**——
只改一句話卻動了十幾個檔案，就要問清楚為什麼。

**Q：可以一次推很多改動嗎？**

可以，但**一個 PR 講一件事**比較好審。
不相關的改動混在一起，半年後想知道某個決定為什麼這樣做會找不到。
