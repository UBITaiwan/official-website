# 修改流程（每一次改動都走這一輪）

> 這是最基本、也最重要的一份。**不管要改什麼，都從這裡開始。**
> 其他 flow 是在這個框架裡處理特定情況。

---

## 什麼時候用

**每一次。**改一個錯字、換一張照片、加一整頁，都一樣。

你只需要說出「我要改 XXX」，**細節不用先想清楚**。
這個流程的設計就是讓 AI 先把工作環境準備好，再回頭跟你確認方向。

---

## 給 AI 的話

開始一段新工作時，整段複製貼給它：

```
請先讀 AGENTS.md 和 flows/修改流程.md，然後照那個流程進行。

我要改的是：（一句話描述要動哪一塊，不確定細節沒關係）
```

這段話對 Claude Code 和 Codex 都適用。兩者讀的入口檔不同
（Claude Code 讀 `CLAUDE.md`、Codex 讀 `AGENTS.md`），但規則是同一套。

---

## 它應該做什麼

照順序，**一步都不要跳**。

### 1. 先站到安全的位置（開分支）

**收到「我要改 XXX」之後的第一個動作不是提問，是開分支。**

先確認沒有沒存好的東西：

```bash
git status --porcelain     # 有輸出就先停下來問，不要往下做
```

取得最新版：

```bash
git checkout main
git fetch origin
git reset --hard origin/main
```

> **⚠️ `reset --hard` 會丟掉本機未提交的改動。**
> 所以上一行的 `git status` 不能省。有輸出時要先問過人，不要自己決定丟掉。

**這一步不能省。**現在有多個人（和 AI）在同一個 repo 上工作，
不先更新就開分支，改完會跟別人的改動打架，而且通常要花更多時間解決。

然後開分支。名稱由 **AI 自己取並告訴你**，你不需要自己想——
它應該把你的中文描述翻成英文短句，加上類別前綴：

| 你說的話 | 分支名稱 |
|---|---|
| 「關於我們那頁，巫彥德的頭銜錯了」 | `fix/about-team-titles` |
| 「我要加 2026 年度報告」 | `feat/annual-2026` |
| 「生活自由計畫要進入下一階段了」 | `chore/life-freedom-timeline` |
| 「首頁那張照片想換掉」 | `chore/home-hero-photo` |
| 「我想介紹三位新理事，但還不確定怎麼呈現」 | `feat/about-new-board-members` |

前綴只有四個：`fix/` 修錯、`feat/` 新增、`chore/` 更新維護、`docs/` 改文件。
**分不出來就用 `chore/`**，前綴取錯不影響任何事。

```bash
git checkout -b fix/about-team-titles
```

**確認自己不在 `main` 上再往下做。**

### 2. 回頭問清楚方向

分支開好了，現在才討論要改成什麼樣子。

AI 應該先把它的理解說一遍，不清楚的地方要問，**不要猜**。
這一輪可能來回好幾次，慢慢聊沒關係——你們是在分支上聊，`main` 不會受影響。

聊完之後你應該看得到：它要改哪些檔案、大概怎麼改、有沒有它做不到的部分。

**如果它已經開始改檔案卻還沒跟你確認過方向，請它停下來。**

### 3. 開始改

依照要改的內容，可能還有對應的 flow 要照著走（見 [README.md](README.md) 的對照表）。

改完之後 AI 應該**主動驗證**，見 `AGENTS.md` 的「改完一定要驗證」。

### 4. 推送前先檢查

```bash
npm run build
npm run check
```

連結、資安、無障礙一次檢查完。**通過才能往下做。**
細節與如何判讀輸出見 [推送前檢查](推送前檢查.md)。

### 5. Commit 並推上分支

```bash
git add -A
git commit -m "說明為什麼這樣改，不只說改了什麼"
git push -u origin fix/about-team-titles
```

commit 訊息要寫**為什麼**。半年後看到「修正文字」什麼都想不起來，
但「頭銜與 2025 年度報告不符，依報告更正」一看就懂。

### 6. 開 PR，你看過再合併

```bash
gh pr create --base main --title "..." --body "..."
```

沒有 `gh` 指令或沒登入時，改用網頁：推上分支之後打開
https://github.com/UBITaiwan/official-website ，頁面上方會出現
「Compare & pull request」按鈕。**兩種做法結果一樣。**

**不要直接推到 `main`。**

AI 應該把 PR 網址給你。你看過「Files changed」確認沒有動到不該動的地方，
再合併。合併之後大約兩三分鐘，dev 站會自動更新：

https://ubitaiwan.github.io/official-website/

## 你要檢查什麼

| | 怎麼看 |
|---|---|
| **它有沒有先開分支？** | 它應該主動告訴你分支名稱。沒講就問「現在在哪一個分支？」，答案不能是 `main` |
| **它有沒有在動手前確認方向？** | 開分支可以自己做，但「要改成什麼樣子」一定要先跟你對過 |
| **只動了該動的地方嗎？** | 在 PR 的「Files changed」看。只改一句話卻動了十幾個檔案，要問為什麼 |
| **有沒有給你驗證結果？** | 建置成功、連結沒失效、圖片有替代文字。只說「改好了」不算 |
| **視覺改動有沒有截圖？** | 沒有畫面就無法判斷 |

## 常見問題

**Q：為什麼不先問清楚再開分支？順序好像顛倒了。**

這是刻意的。「問清楚」可能要來回好幾輪，而這段期間 AI 手上必須
已經有一個安全的位置可以動手。先開分支有三個好處：

- 討論到一半如果它逕自動手，改到的是分支，不是 `main`
- 討論時它讀到的是**最新**的程式碼，不是擱了兩週的舊版
- 分支開錯、名字取錯都能改；在 `main` 上動手是沒有回頭路的

**代價只有一個**：聊完發現不用改，就把分支丟掉，不影響任何事。

**Q：我只是想問問題，不想改東西。**

跟它說「我只是想了解，這次先不要改」。它就不會開分支。

**Q：聊完發現方向跟分支名稱對不上了？**

請它改名就好，還沒推上去的分支改名沒有任何成本：

```bash
git branch -m 新名稱
```

**Q：可以直接改 `main` 嗎？**

不要。`main` 一有改動就會自動部署到 dev 站，沒有回頭的機會。
走分支的話，PR 合併前都可以丟掉重來。

**Q：AI 說「已經在 main 上 commit 了」怎麼辦？**

跟它說：

> 請把這些 commit 移到新分支，並把 main 還原成遠端的版本。

這是可以救的，而且在合併前救都還來得及。

**Q：分支改到一半想放棄？**

直接不管它就好，或跟 AI 說「這個分支不要了，請切回 main」。
沒有合併的分支不會影響任何東西。

**Q：改壞了，dev 站爛掉怎麼辦？**

跟 AI 說「請把網站回復到上一個正常的版本」。
每一次合併都是一個可回復的點。

**Q：一定要開 PR 嗎？可不可以直接合併？**

PR 的價值在於**留下紀錄**——半年後想知道某個改動為什麼這樣做，
PR 說明會告訴你。直接合併就沒有這層紀錄。
