# 修改流程（每一次改動都走這一輪）

> 這是最基本、也最重要的一份。**不管要改什麼，都從這裡開始。**
> 其他 flow 是在這個框架裡處理特定情況。

---

## 什麼時候用

**每一次。**改一個錯字、換一張照片、加一整頁，都一樣。

你只需要說出「我要改 XXX」，**細節不用先想清楚**。
這個流程的設計就是讓 AI 先把工作環境準備好，然後直接改給你看，你看了覺得不對再調整。

---

## 給 AI 的話

開始一段新工作時，整段複製貼給它：

```
請先讀 AGENTS.md 和 flows/修改流程.md，然後照那個流程進行。

我要改的是：（一句話描述要動哪一塊，不確定細節沒關係）
```

這段話對 Claude Code 和 Codex 都適用。兩者讀的入口檔不同
（Claude Code 讀 `CLAUDE.md`、Codex 讀 `AGENTS.md`），但規則是同一套。

---

## 它應該做什麼

照順序，**一步都不要跳**。

### 1. 先站到安全的位置（開分支）

**收到「我要改 XXX」之後的第一個動作不是提問，是開分支。**

先確認沒有沒存好的東西：

```bash
git status --porcelain     # 有輸出就先停下來問，不要往下做
```

取得最新版：

```bash
git fetch origin
```

如果 `git fetch origin` 失敗，先處理錯誤，再開分支。

**這一步不能省。**現在有多個人（和 AI）在同一個 repo 上工作，
不先更新就開分支，改完會跟別人的改動打架，而且通常要花更多時間解決。

然後開分支。名稱由 **AI 自己取並告訴你**，你不需要自己想——
它應該把你的中文描述翻成英文短句，加上類別前綴：

| 你說的話 | 分支名稱 |
|---|---|
| 「關於我們那頁，巫彥德的頭銜錯了」 | `fix/about-team-titles` |
| 「我要加 2026 影響力報告書」 | `feat/reports-2026` |
| 「生活自由計畫要進入下一階段了」 | `chore/life-freedom-timeline` |
| 「首頁那張照片想換掉」 | `chore/home-hero-photo` |
| 「我想介紹三位新理事，但還不確定怎麼呈現」 | `feat/about-new-board-members` |

前綴只有四個：`fix/` 修錯、`feat/` 新增、`chore/` 更新維護、`docs/` 改文件。
**分不出來就用 `chore/`**，前綴取錯不影響任何事。

```bash
git switch --no-track -c fix/about-team-titles origin/main
```

新分支從 GitHub 的最新版 `origin/main` 建立，並保留本機 `main` 的提交。推送時再設定新分支追蹤自己的遠端分支。

**確認自己已切換到新分支再往下做。**

### 2. 直接改，改完給對方看

分支開好了，**直接動手，不用先問方向**。改完用白話講給對方聽，對方看了想調整再改。

這樣做是因為對方不是工程人員：讀一段「我打算這樣做」很難判斷對不對，
看到改好的畫面就知道了，通常一輪就能定案。改錯了也沒關係，
所有改動都在分支上，推上去之前對方還會再看一次（第 4 步起）。

**只有 2-4 列的四種情況要先停下來問。**

#### 2-1 確認本機預覽有在跑

對方是看自己電腦上的本機預覽（`npm run dev`，通常是 `http://localhost:4321`），
即時看到改動的樣子。動手前先確認它有在跑，沒有的話幫忙開起來，
並把網址給對方（見[本機預覽與環境檢查](本機預覽與環境檢查.md)）。

環境還沒裝好、跑不起來時，先照那份處理，不要先改檔案。
對方不想在自己電腦上裝東西時，改成每次改完截圖給對方看（見 2-3）。

#### 2-2 直接改

依照要改的內容，可能還有對應的 flow 要照著走（見 [README.md](README.md) 的對照表）。

- 寫網站上的文字之前，先讀[寫作規範](../寫作規範.md)
- **只改這次要改的頁面**，不要順手動共用的樣式與元件（見 `AGENTS.md`「不可以做的事」第 6 項）
- **需要選擇的地方，挑你最推薦的做法直接做**，不要把選擇題丟回去。
  例如首頁有兩個「認識基本收入」，挑最可能的那個改，改完說明
- 對方說得很模糊（「這段太長，精簡一點」），就直接寫一個版本放上去給對方看
- **大的需求先做一小塊**。例如「首頁改版」，先改一個區塊給對方看方向對不對，
  不要一口氣全部做完才發現方向錯了
- 缺素材時，先去 `public/images/` 找現有的照片（**打開看過**再用，不可憑檔名判斷）。
  改完順便提一句「如果你手上有更合適的照片或文件，可以直接丟給我」，但不要因為沒有素材就停下來等

改完 AI 要**自己先驗證**，見 `AGENTS.md` 的「改完一定要驗證」。
視覺上的改動 AI 要自己看過（包括手機寬度），不能只說「改好了」。

#### 2-3 改完講三件事，而且要講人話

1. **改了什麼、去哪裡看**：給本機預覽上的網址，並說在頁面的哪裡
   （例如「打開 localhost:4321/ubi/，往下捲到『五大元素』那一區」）
2. **我替你做了哪些決定**：例如「首頁有兩個『認識基本收入』，我改的是最上面的按鈕；
   如果你指的是區塊標題，說一聲」。沒有就不用講
3. **畫面上看不出來、但我也動到的地方**：連結網址、圖片的說明文字、
   瀏覽器分頁上的標題、別頁的同一句話。沒有就不用講

自己驗證過的部分用一句話帶過即可，例如「手機寬度我看過了，沒有爆版」。

**不用每次都附截圖**，對方開著本機預覽就看得到。只有下面這幾種，
對方直接看本機預覽不容易看到，才主動附圖：

| 情況 | 為什麼要附圖 |
|---|---|
| 手機上的樣子 | 對方要開開發者工具才能切換，多半不會去切 |
| 改之前的樣子 | 本機預覽只顯示改完的版本。改設計時附改前、改後對照 |
| 別頁也被改到 | 對方只會看自己那頁 |
| 要點開或等一下才出現的內容 | 收合的問答、選單的下拉項目、首頁輪替的字 |
| 對方沒有開本機預覽 | 例如對方不想在自己電腦上裝東西，或說「截圖給我看」 |

改了樣式、對方卻說沒看到變化時，請對方**強制重新整理**
（Windows 按 `Ctrl` + `Shift` + `R`，Mac 按 `Cmd` + `Shift` + `R`）。
本機預覽有時會沿用舊的樣式表（見 `AGENTS.md`「已知的陷阱」）。

**對方不是工程人員，講法要跟著換。**同一件事有兩種說法：

| ❌ 不要這樣說 | ✅ 要這樣說 |
|---|---|
| 「我在 `ubi-content.json` 新增了一個 object」 | 「我把這一題加進大哉問的題目清單了」 |
| 「調整了首屏 hero 的 object-position」 | 「那頁最上面那張大照片，構圖往下移了一點，人臉不會被切到」 |
| 「這個 CTA 的對比不足」 | 「這顆按鈕顏色太淺，視力比較弱的人會看不清楚」 |
| 「建立了 redirect stub」 | 「舊網址會自動跳到新網址，以前的連結不會失效」 |
| 「mobile viewport 會 overflow」 | 「手機上會爆版，要左右滑才看得完」 |
| 「把這段抽到 data 層」 | 「把這些文字集中放到一個地方，以後要改比較好找」 |

檔名、路徑、技術名詞**不是不能講**，但要放在括號裡當補充，不要當主詞。
對方要判斷的是「這樣對不對」，不是「你動了哪個檔案」。

#### 2-4 這四種情況要先停下來問

猜錯的代價不只是「重改一次」時，才先問。**只問卡住的那一點**，其他能做的照常做。
一次要改好幾處時，沒卡住的直接改，卡住的整理成一則訊息一次問完。

| 情況 | 為什麼不能先做 | 怎麼問 |
|---|---|---|
| **缺事實的來源**：數字、日期、人名、頭銜、引言，對方沒給、網站和文件裡也查不到 | 猜了就是在網站上寫錯事實（見寫作規範「事實要查證」） | 「這裡要寫幾位志工？」 |
| **會影響別人負責的頁面**：要動共用檔案，或同一句話、同一個事實（數字、名稱、日期）也出現在別頁 | 只改一頁，網站上的說法就前後不一致；全部改，又動到別人的頁面 | 「實驗總覽頁和生活自由計畫頁也寫 3 位，要一起改嗎？」 |
| **會蓋掉或刪掉別人的內容**：對方給的文件比網站舊、刪掉整個區塊或整頁 | 本機預覽上看起來沒問題，其實把別人改好的地方改回去了 | 「文件裡有兩處跟網站不同，是後來別人改的，要保留網站現在的版本嗎？」 |
| **跟現有規定衝突**：捐款按鈕、別人的作品標題、寫作規範的用詞 | 這是協會的決定，不是一位負責人能改的 | 先改成符合規定的寫法，說明原因，再問對方能不能接受 |

第四種的用詞衝突**不能只靠自動檢查**：
自動檢查會擋破折號和缺空格，但抓不到「本會」（規範寫「我們」）
或把 BIEN 印太高峰會寫成「BIEN 高峰會」這類錯誤，要自己對照寫作規範。

對方說「**先講給我聽再動**」時，就改回先講再做：講你理解的需求、打算怎麼做、
改完會看到什麼，等對方說可以再動手。

##### 動手前要查的事

前面四種情況要實際查過才知道，不要憑對方的描述判斷：

- **搜尋要搜兩個地方**：原始檔，以及建置出來的頁面（`npm run build` 之後的 `dist/`）。
  有些畫面上的字是程式拼起來的（例如首頁輪替的「安心、自由、快樂……」），只搜原始檔會找到 0 處。
  搜到 0 處時也可能是舊網站的字，要問對方是在哪裡看到的
- **「首頁的 X」不代表網站上只有一個 X**：同一句話可能也在選單或別頁出現
- **改到數字、名稱、日期時，用那個數字或名稱本身去搜**，不要只搜整句。
  同一個事實在各頁的寫法常常不一樣，例如首頁寫「3 位主角」、實驗總覽頁寫「參與主角：3 位」
- **看一下有沒有別人還沒合併的修改動到同一個檔案**（`gh pr list`）。
  有的話不用停下來，但要告訴對方，合併時可能要處理衝突
- **刪東西之前，查有沒有別的地方連到它**：刪掉一個區塊，別處跳到那一區的按鈕就失效，
  自動檢查只會提醒、不會擋下

##### 對方給截圖時

- 從截圖上的字去搜原始檔，找到是哪一頁、哪一段
- 圈起來的範圍跟新文字對不上時（例如圈了整句，新文字只對應後半句），
  照最合理的理解改（通常是保留沒提到的部分），改完說明
- **照片裡的字改不了**（白板、手舉牌、布條上的字是照片的一部分），要跟對方說明
- 「這邊是不是寫錯了？」是在問問題，先查清楚再回答，不要直接改

##### 對方給文件或貼一整段時

**先跟網站現在的文字逐句比對，把差異找出來。**對方提到的差異、明顯是新加的內容，直接改。
比對出對方沒提到的差異時要先問（2-4 的第三種）。最常見的原因是**文件比網站舊**：
對方很久以前複製了一份，後來別人改過網站，照文件整段貼上就會把別人的修改改回去。

##### 實際試過的例子

| 對方說的話 | 查到的情況 | 怎麼做 |
|---|---|---|
| 「首頁的『已經有人填過了』改成『已經有人說過了』」 | 網頁上只有一處 | 直接改 |
| 「這句改成『2026年開始』」 | 少了空格，屬於格式問題 | 直接改，補上空格並說明 |
| 「首頁按鈕『認識基本收入』改成一句比較長的話」 | 首頁有按鈕、區塊標題、選單三處 | 改按鈕（對方說了「按鈕」），說明另外兩處沒動 |
| 「首頁的『安心、自由、快樂』改成……」 | 原始檔搜不到，是程式拼出來的 | 搜建置後的頁面找到出處，直接改 |
| 一次五項：三處改字、拿掉一顆按鈕、某顆按鈕換顏色 | 都只在首頁 | 全部直接改；換顏色附改前、改後對照圖 |
| 「四種力量那區的圖示放大到 96」 | 只改大小，串連圖示的細線會對不準 | 直接改，線的位置一起調；附改前、改後對照圖 |
| 「這裡改成『本會將於2027年舉辦BIEN高峰會——歡迎參加』」 | 缺空格、破折號、「本會」、活動名稱不對 | 改成符合規範的寫法，逐項說明（第四種） |
| 截圖圈起整句說明文字，備註只寫了後半句的新文字 | 照字面換會丟掉年份和活動名稱 | 保留前半句，只換後半句，改完說明 |
| 截圖圈起照片裡白板上的字，問「是不是寫錯了？」 | 那是參與者的手寫字，照片改不了 | 說明，不改 |
| 一份 Word 檔，請把兩段換成新版 | 比對出四處差異，其中兩處會把別人的修改改回去 | 改對方想改的兩處，另外兩處先問（第三種） |
| 「首頁那段太長，精簡一點」 | 沒給改完的文字 | 直接寫一個精簡版放上去 |
| 「首頁『認識基本收入』那一區刪掉」 | 整區刪除，首頁最上面的按鈕會跳到這一區 | 先問（第三種），並說明那顆按鈕要怎麼處理 |
| 「『生活自由計畫』改名」 | 好幾頁都有，選單和頁尾也有 | 先問：全站一起改嗎？（第二種） |
| 「某位講者的頭銜改一下」 | 沒給新頭銜；而且好幾頁都有，影響力報告書是當年的紀錄 | 先問新頭銜，以及哪幾頁要改（第一、二種） |
| 「捐款按鈕改成『前往捐款』」 | 違反捐款按鈕全站統一的規定 | 不改，說明規定（第四種） |
| 「新聞標題裡有錯字，幫我改」 | 別人的作品標題要照原文 | 不改，說明規定（第四種） |
| 「志工人數更新一下」 | 沒給新數字 | 先問數字（第一種） |
| 「首頁的 3 位主角改成 5 位」 | 實驗總覽頁、生活自由計畫頁也寫 3 位，句子都不一樣 | 先問：別頁要一起改嗎？（第二種） |

### 3. 改的時候要注意

- 有對應 flow 的工作照 flow 做（見 [README.md](README.md) 的對照表）
- 同一個分支可以來回改很多次，對方看了說「這裡再調一下」就繼續改，不用每次都重開分支
- 想要的改動都完成了，跟對方說可以推上去了（第 4 步）

### 4. 推送前先檢查

> 第 4 到第 6 步可以一次交代完：跟 AI 說「**我要推上去**」，
> 它會照 [推上去](推上去.md) 把校稿、檢查、最後確認、commit、push、開 PR 一路做完。
> 下面是那三步的摘要。有改到文字的話，檢查之前會先 [校稿](校稿.md)；
> 送出前會請你在預覽網頁上看過最後的樣子，你說可以才送。

```bash
npm run build
npm run check
```

連結、資安、無障礙、文字一次檢查完。**通過才能往下做。**
細節與如何判讀輸出見 [推送前檢查](推送前檢查.md)。

### 5. Commit 並推上分支

```bash
git add -A
git commit -m "說明為什麼這樣改，不只說改了什麼"
git push -u origin fix/about-team-titles
```

commit 訊息要寫**為什麼**。半年後看到「修正文字」什麼都想不起來，
但「頭銜與 2025 影響力報告書不符，依報告更正」一看就懂。

### 6. 開 PR，你看過再合併

```bash
gh pr create --base main --title "..." --body "..."
```

沒有 `gh` 指令或沒登入時，改用網頁：推上分支之後打開
https://github.com/UBITaiwan/official-website ，頁面上方會出現
「Compare & pull request」按鈕。**兩種做法結果一樣。**

**不要直接推到 `main`。**

AI 應該把 PR 網址給你。你看過「Files changed」確認沒有動到不該動的地方，
再合併。合併之後大約兩三分鐘，dev 站會自動更新：

https://ubitaiwan.github.io/official-website/

## 你要檢查什麼

| | 怎麼看 |
|---|---|
| **它有沒有先開分支？** | 它應該主動告訴你分支名稱。沒講就問「現在在哪一個分支？」，答案不能是 `main` |
| **改完有沒有講清楚？** | 它應該告訴你去哪裡看、替你做了哪些決定、有沒有動到畫面上看不出來的地方。只說「改好了」不算 |
| **它講的你聽得懂嗎？** | 滿是檔名和英文術語就請它重講。這不是你的問題，是它沒照流程做 |
| **只動了該動的地方嗎？** | 在 PR 的「Files changed」看。只改一句話卻動了十幾個檔案，要問為什麼 |
| **有沒有給你驗證結果？** | 建置成功、連結沒失效、圖片有替代文字。只說「改好了」不算 |
| **該停下來問的有沒有問？** | 缺數字或人名、會改到別人的頁面、會蓋掉別人的內容、跟網站規定衝突時，它應該先問你（見 2-4） |

## 常見問題

**Q：為什麼不先問清楚再開分支？順序好像顛倒了。**

這是刻意的。「問清楚」可能要來回好幾輪，而這段期間 AI 手上必須
已經有一個安全的位置可以動手。先開分支有三個好處：

- 討論到一半如果它逕自動手，改到的是分支，不是 `main`
- 討論時它讀到的是**最新**的程式碼，不是擱了兩週的舊版
- 分支開錯、名字取錯都能改；在 `main` 上動手是沒有回頭路的

**代價只有一個**：聊完發現不用改，就把分支丟掉，不影響任何事。

**Q：它講的我聽不懂怎麼辦？**

直接說：

> 請用白話文再講一次，不要提檔名和技術名詞。

**它有義務講到你聽得懂。**你聽不懂就無法判斷對不對，
那個確認就失去意義了——照著點頭等於沒看過。

**Q：我沒有照片或文件，是不是就不能改？**

不是。先讓它去找現有的素材：

> 你先看看現有的照片裡有沒有能用的，真的沒有再跟我說缺什麼。

`public/images/` 裡有大量還沒用到的真實照片。
如果它一開口就說「請提供素材」而沒有先找過，請它先找。

**Q：它一次給我兩三個做法，要我選，但我不知道怎麼選。**

問它：

> 你建議哪一個？為什麼？

它應該要有推薦，而且說得出取捨。
答不出來的話，那幾個做法通常它自己也沒想清楚。

**Q：它沒問我就直接改了，這樣對嗎？**

對，這是刻意的。看到改好的畫面，比讀一段「我打算這樣做」容易判斷。
不喜歡就說「改回去」或「換個方式」，都在分支上，沒有任何損失。

如果這次你想先聽它的想法，跟它說：

> 先講給我聽再動。

**Q：我只是想問問題，不想改東西。**

跟它說「我只是想了解，這次先不要改」。它就不會開分支。

**Q：聊完發現方向跟分支名稱對不上了？**

請它改名就好，還沒推上去的分支改名沒有任何成本：

```bash
git branch -m 新名稱
```

**Q：可以直接改 `main` 嗎？**

不要。`main` 一有改動就會自動部署到 dev 站，沒有回頭的機會。
走分支的話，PR 合併前都可以丟掉重來。

**Q：AI 說「已經在 main 上 commit 了」怎麼辦？**

跟它說：

> 請把這些 commit 移到新分支，並把 main 還原成遠端的版本。

這是可以救的，而且在合併前救都還來得及。

**Q：分支改到一半想放棄？**

直接不管它就好，或跟 AI 說「這個分支不要了，請切回 main」。
沒有合併的分支不會影響任何東西。

**Q：改壞了，dev 站爛掉怎麼辦？**

跟 AI 說「請把網站回復到上一個正常的版本」。
每一次合併都是一個可回復的點。

**Q：一定要開 PR 嗎？可不可以直接合併？**

PR 的價值在於**留下紀錄**——半年後想知道某個改動為什麼這樣做，
PR 說明會告訴你。直接合併就沒有這層紀錄。
