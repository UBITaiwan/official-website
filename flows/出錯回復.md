# 出錯回復（改壞了要復原）

> **先看這一句：幾乎所有情況都救得回來，而且不急。**
> 唯一真正救不回來的，是「還沒存檔的改動被丟掉」。其他每一步都留著紀錄。

---

## 什麼時候用

- 改完發現不對，想退回去
- dev 站看起來怪怪的
- AI 說它不小心動到 `main`
- 不知道發生了什麼事，但覺得哪裡不對勁

---

## 最重要的一件事：先停下來

**不要讓 AI「順手修一下」。**先搞清楚壞在哪一層，再決定怎麼救。
越急越容易把「可以救的」變成「救不回來的」。

網站壞掉不會有人受傷，dev 站也沒有對外公開。**慢慢來沒有關係。**

---

## 給 AI 的話

```
先不要動任何東西。請先告訴我現在的狀況：
現在在哪一個分支、有沒有還沒存的改動、
main 的最後一次改動是什麼、最近一次部署成功了沒。
```

---

## 它應該做什麼

### 1. 先判斷壞在哪一層——這一步不要動手

```bash
git status                          # 現在在哪個分支、有沒有還沒存的改動
git log --oneline -5                # 這個分支最近改了什麼
git log --oneline -3 origin/main    # 遠端的 main 現在是什麼
gh run list --limit 3               # 最近的部署成功了沒
```

| 壞在哪一層 | 怎麼看出來 | 往下看 |
|---|---|---|
| 檔案改爛了，**還沒存進版本紀錄** | `git status` 列出一堆修改中的檔案 | **A** |
| 存了，但**還在分支上、沒合併** | 現在不在 `main` 上，PR 還沒合併 | **B** |
| **已經合併進 `main`** | `origin/main` 上有那一筆 | **C** |
| **部署失敗** | `gh run list` 顯示 failure | **D** |

**判斷錯了會救錯方向**，所以這一步要先講給對方聽，再往下做。

### A. 還沒存進版本紀錄

```bash
git restore <檔案>     # 還原單一檔案
git restore .          # 還原全部
```

> ⚠️ **這是整份流程裡唯一救不回來的動作。**還沒存的改動丟掉就沒了。
> **一定要先問過對方**，而且要講清楚「你這段時間改的東西會消失」。
> 對方不確定的話，先幫他存成一個分支再說——存了就救得回來。

### B. 存了，但還在分支上

**最簡單的做法：不要那個分支就好。**

```bash
git checkout main
```

沒有合併的分支不影響任何東西，**留著也沒關係**，不用刻意刪。

只想退掉最後一次存檔、但保留改動的話：

```bash
git reset --soft HEAD~1    # 改動留在檔案裡，只是取消那一次存檔
```

### C. 已經合併進 `main`

`main` 一有改動就會自動部署到 dev 站，所以這時候 dev 站已經是壞的版本了。

**用「反悔」的方式還原，不要改寫歷史。**
做法是產生一筆反向的改動把它抵銷掉，原本的紀錄完整保留。

**做法一：在 GitHub 網頁上按鈕（推薦）**

打開那個已經合併的 PR，頁面下方有 **Revert** 按鈕。
按下去會自動開一個新的 PR，合併它就還原了。
**這是最不容易出錯的方式**，而且全程有紀錄。

**做法二：用指令**

```bash
git checkout main
git fetch origin
git reset --hard origin/main
git checkout -b fix/revert-說明一下還原什麼
git revert <要還原的那次改動的代碼>
```

然後照 [修改流程](修改流程.md) 開 PR。
這個 repo 沒有 merge commit（歷史是線性的），所以 `git revert` 不用加額外參數。

> **一個 PR 不一定只留下一筆。**
> 這個 repo 用 rebase 合併：PR 裡有幾個 commit，合併後就在 `main` 上留下幾筆。
> 所以「還原那次 PR」常常不是還原一筆，而是一整段。
>
> **這正是推薦用網頁那顆 Revert 按鈕的原因**——不管一個 PR 有幾筆，
> 它都會一次還原整個 PR，不用自己數。用指令的話要給一段範圍：
>
> ```bash
> git revert --no-edit <那個 PR 最舊的一筆>^..<最新的一筆>
> ```
>
> 會產生同樣數量的還原 commit。**先確認自己抓對範圍再執行。**

> **為什麼不直接把那筆改動刪掉？**
> `main` 目前**沒有設分支保護**，技術上真的做得到。但那會改寫歷史：
> 其他人手上的版本會對不上，而且已經部署出去的東西也不會因此消失。
> **反悔比較笨，但安全。**

### D. 部署失敗

**先講好消息：網站沒有壞。**

部署流程設定成「建置成功才會發布」（`deploy` 要等 `build` 成功）。
所以建置失敗時新版本根本不會上去，dev 站會**停在上一個成功的版本**。
這是「網站沒更新」，不是「網站壞了」。

先看失敗的原因：

```bash
gh run list --limit 5
gh run view <編號> --log-failed
```

修好之後推上去會自動重跑。也可以手動重跑：

```bash
gh run rerun <編號>                              # 重跑那一次
gh workflow run "Deploy to GitHub Pages (dev)"   # 用現在的 main 重新部署一次
```

### 2. 救完要確認，不要只說「好了」

- 合併之後 dev 站要等**兩三分鐘**才會更新
- 確認 `gh run list` 最新一筆是 success
- 打開 https://ubitaiwan.github.io/official-website/ 實際看過
- 視覺上的問題要**截圖**給對方看，不要只說「還原了」

---

## 你要檢查什麼

| | 怎麼看 |
|---|---|
| **它有沒有先講清楚壞在哪一層？** | 沒搞清楚就開始救，很容易越救越糟 |
| **它要不要丟掉你的東西？** | 「還沒存的改動」丟掉就沒了，**一定要先問過你** |
| **它有沒有提到改寫歷史？** | 看到「force push」「強制推送」「reset main」就先喊停，問它「用 revert 可以嗎」 |
| **還原之後有沒有重新確認？** | 要看到部署成功，而且實際打開網站看過 |

## 常見問題

**Q：dev 站看起來怪怪的，是不是壞了？**

先硬重新整理（Mac 按 `Cmd` + `Shift` + `R`，Windows 按 `Ctrl` + `F5`）。
還是怪的話，請 AI 看最近一次部署成功了沒。

**Q：可以回到「上禮拜那個版本」嗎？**

可以。每一次合併都是一個可以回去的點。跟 AI 說：

> 請還原到「XXX」那次改動之前。

用你記得的說法描述就好，它會去找對應的紀錄。

**Q：AI 說要 force push，或說要把 main 重設，可以嗎？**

**先不要。**`main` 目前沒有保護，它真的做得到。
先問它：

> 用 revert 可以達到一樣的效果嗎？

九成的情況可以。真的必須改寫歷史時，它要說得出為什麼 revert 不行。

**Q：我把分支刪掉了，東西還在嗎？**

還沒合併的分支刪掉後，短期內通常還找得回來。
跟 AI 說分支名稱與大概的時間，請它找找看。
**但不要拖**——放久了就真的沒了。

**Q：最壞的情況是什麼？**

「還沒存進版本紀錄的改動被丟掉」是唯一真正救不回來的。
所以那一個動作**永遠要先問過你**。其他每一種情況都有紀錄可以回去。
